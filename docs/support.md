# 平台与能力范围

本文描述 `0.4.0` 内测版本的能力，核对日期为 2026-11-22。
版本与发布状态以 [README](../README.md) 为准；历史验收证据见 [交付清单](release-checklist.md)。

## 平台

| 平台 | 当前依赖切片 | 当前范围 |
|---|---|---|
| iOS / iPadOS 真机 | arm64 | 内测接入范围；已有 iPad 真机验收 |
| iOS 模拟器 | arm64、x86_64 | 可构建；不能替代硬件解码、HDR、音频路由和画中画的真机验收 |
| 原生 macOS | arm64、x86_64 | 内测接入范围；已有 Mac 播放与归档验收 |
| Mac Catalyst | 无 | 暂不支持 |
| tvOS | 无 | 暂不支持 |
| visionOS | 无 | 暂不支持 |

三个依赖 xcframework 的当前切片范围一致。原生 macOS 与 Mac Catalyst 使用不同的构建目标；macOS 切片不能替代 Catalyst 切片。
`Package.swift` 还声明了扩展平台的最低版本，这不代表已交付对应依赖或完成验证。
当前 iOS 15、macOS 12 是包声明的部署下限，不代表每个系统版本、设备和编码组合都已实测。

## 播放与输出

| 能力 | 当前行为与边界 |
|---|---|
| 数据源 | 内置本地文件、HTTP、内存缓冲包装与磁盘字节缓存；自定义来源经 `UmbelSource` 注入 |
| 网络直播 | `UmbelLiveHTTPSource`（HTTP-FLV、HTTP-TS 等不结束的 HTTP 响应）、`UmbelNetworkStreamSource`（`rtmp`、`rtmps`、`rtmpt`、`rtmpts`、`udp`、`tcp`）与 `UmbelRTPStreamSource`（`rtsp`、`rtp`）。顺序读、不能 seek，断流报 `sourceUnavailable`，来源内不重连、是否重开由宿主决定；其他协议的地址报 `unsupportedScheme`。连接由 FFmpeg 自己建立，不走系统代理与 App Transport Security，除 `rtmps`、`rtmpts` 外都不加密；`rtsp`、`rtp` 的流结束也算断流。`rtmps` 经系统 TLS，证书一律校验，已在本机真实服务器上验证；`rtmpts`（TLS 隧道）尚未在真实服务器上验证 |
| FTP | `UmbelFTPSource`：`ftp://` 上的文件，随机读、可 seek，明文，不重试；读取被取消时放弃并重连 |
| SRT | 可选模块 `UmbelSRTSource`：`srt://主机:端口`，播放端作调用方；可选口令加密（10 到 79 个字符，认证加密用随库链接的 OpenSSL）。顺序读、不能 seek，断流与发送端结束都报 `sourceUnavailable`；需先构建 `UmbelSRT.xcframework`。加密、错口令被拒、取消、释放已用 SRT 自己的对端验证；对着 mediamtx 的 SRT 服务读取已在本机与 iPad 真机验证（数据正确）；真实的 SRT 发送设备与丢包网络下的行为未验证 |
| SFTP | 可选模块 `UmbelSFTPSource`：`sftp://用户@主机[:端口]/路径`，随机读、可 seek，加密。**主机密钥必须由调用方判定**（`hostKeyVerifier`，或 `UmbelSFTPSource.trusting(fingerprints:)` 给一份可信指纹），没有默认信任，也没有跳过的办法；密钥不被信任时，在发出任何凭据之前断开。登录用私钥（含带口令的）或密码；需先构建 `UmbelSSH2.xcframework`。已用本机 `sshd` 验证各种私钥、主机密钥校验与其顺序、错私钥与错口令被拒、缺文件、连接与停滞超时、取消后重连；密码登录的成功路径未验证（非 root 的 `sshd` 校验不了密码），真实 NAS 与大文件长时间读取未验证 |
| RIST | 可选模块 `UmbelRISTSource`：`rist://主机:端口`，播放端作调用方（发送端监听）；Main 与 Advanced 档位；可选预共享口令加密（`secret`，默认 AES-256，可 `aes-type=128`）与恢复缓冲区（`buffer`，毫秒）。顺序读、不能 seek，断流与发送端结束都报 `sourceUnavailable`；RIST 不校验口令，口令不对时得到的不是码流（没有数据或是乱码）。不提供 Simple 档位（它的发送端把流推给等待的接收端，而调用方不是等待方）与 SRP；需先构建 `UmbelRIST.xcframework`。已用 librist 自己的发送端在本机验证：收发、加密、地址里口令含特殊字符、中继丢包后的重传、各类超时与取消；真实的 RIST 设备与广域网丢包未验证 |
| SMB | 可选模块 `UmbelSMBSource`：`smb://[域;][用户[:密码]@]主机[:端口]/共享/路径`，随机读、可 seek。登录是 NTLM，地址里没有用户就是来宾（来宾不能签名也不能加密，所以只讲 SMB 2）；没有 Kerberos。服务器要求签名时自动签名；`requireEncryption` 要求 SMB 3 加密，服务器不加密就拒绝。LGPL：`UmbelSMB2.framework` 是只含 libsmb2 的独立动态库，App 可以替换；需先构建 `UmbelSMB2.xcframework`。已用本机 Samba 验证：整读、任意位置读、越界、子目录与空格、口令与用户错误、共享与文件不存在、来宾、要求签名的服务器、加密、连接与停滞超时、取消后重连；真实 NAS、Windows 共享、域登录与 SMB 3.1.1 之外的各种服务器未验证 |
| NFS | 可选模块 `UmbelNFSSource`：`nfs://主机[:端口]/导出路径/文件`（文件是最后一个名字，导出是它所在的目录；或用 `?export=` 指明导出），随机读、可 seek。NFS 版本 3、TCP、`AUTH_SYS`：**没有登录、没有加密**，服务器只信客户端自报的用户与组（`userID`、`groupID`），文件内容在网络上是明文，只适合可信网络。不找嵌套在下面的导出，不提供 Kerberos、TLS、NFSv4；MOUNT 服务不在端口映射器上的服务器要 `?mountport=`。LGPL：`UmbelNFS.framework` 是只含 libnfs 的独立动态库，App 可以替换；需先构建 `UmbelNFS.xcframework`。libnfs 创建连接时让整个进程忽略 `SIGPIPE`。已用测试里自己写的最小 NFSv3 服务（按 RFC 1813）验证：整读（按服务器说的读大小分片）、任意位置读、越界、子目录、用户与组、导出或文件不存在、服务器拒绝挂载、连接与停滞超时、取消后重连、不调用任何会改动文件的过程；真实的 NFS 服务器（Linux、NAS、macOS）、端口映射器路径、nfsv4 都未验证 |
| HLS | 经数据源协议打开播放列表与子资源；直播及仅顺序读取的来源不能任意 seek |
| 播放控制 | 播放、暂停、seek、音轨选择、音量、静音、0.5–2 倍速；seek 能力以 `isSeekable` 为准 |
| 后向缓存 | 可配置已消费音视频压缩包的共享字节预算，默认关闭；可 seek 点播且声音由引擎解码时，关键帧、连续音视频及所选字幕历史完整则复用，未命中走普通 seek；最旧历史优先淘汰，视频保留边界落在关键帧；预算只计包载荷，不是播放器总内存，详见 [接口说明](playback-controls.md#backward-seek-cache) |
| 视频解码 | 系统硬件与软件解码路径；AV1 软件解码已纳入当前依赖；可显式选择同步或引擎级异步提交，默认同步，具体支持取决于码流与设备 |
| HDR | Metal 路径根据显示条件输出扩展动态范围或映射到 SDR；不承诺所有输出路径保留 HDR |
| 字幕 | 文字、ASS、位图，内嵌轨道与外挂字幕（含 PGS `.sup`）；双字幕独立选择、延迟、缩放、位置与底部避让。ASS 由 libass 绘制，静止的画面只画一次，随时间变化的行（`\t`、`\move`、`\fad`、卡拉 OK、Effect 字段非空）每 16 ms 字幕时间至多重画一次；字体由 `setSubtitleFonts(_:)` 提供，`subtitleRenderStatistics` 报告绘制次数、最长耗时与缺字形次数，详见 [接口说明](playback-controls.md#ass-subtitle-drawing)。**iOS 的系统中文字体 libass 用不了**（字形存在 FreeType 不认识的表里），ASS 字幕要显示汉字，宿主必须提供含汉字的字体，否则显示为方框，且每次绘制都很慢；这一点在 iOS 18.6 与 26.5 模拟器的系统字体上查实，真机的系统字体未枚举，修复前后的耗时只在 iOS 18.6 模拟器上量过 |
| 进度预览 | 按时间生成独立缩略图，返回实际帧时间；可取消，不改变当前播放位置；直播、不可定位来源与 P5 系统路径不支持 |
| 画面比例与截图 | 像素路径支持比例覆盖与截图；截图需要已呈现画面，系统压缩码流路径有额外限制 |
| 去隔行 | 标为隔行的帧逐场输出为逐行画面（运动自适应：静止处织入、运动处沿边缘方向插值），所有像素出口一致；`setDeinterlacing(.off)` 关闭，从下一个解出的帧起生效。只认流的隔行标记，不猜未标记的片子，不做反胶转；DV P5 系统显示路径不经过。隔行片每秒画面数翻倍，间隔按场计。4:2:2、4:1:1、4:4:4 的隔行源转成 4:2:0 时按场分别转换，色度行仍分属各自的场。GPU 不可用或某次处理失败时该帧原样显示。已知限制：HEVC 与 VVC 不把两场配成一帧，场编码的流仍按场原样显示、不去隔行；两场分成两个包（如 TS 中按场打包的 H.264）的流，第二场的时间依靠流自己声明的帧率推出，没有声明时可能偏早；帧时长、声明帧率、标称帧率都没有（声明或标称的值不在每秒 10 到 62.5 帧之间，如写成系统时钟的 27 MHz，按没有算）的流，第二场的时间由相邻帧的显示时间推出（连续两个间隔一致才采信，开头两帧只出第一场，每秒 10 帧以下的片源不适用） |
| 显示旋转 | 流声明的四个直角旋转（手机竖拍）在窗口、画中画、快照与进度预览中转正；带翻转或非直角的声明按未旋转处理。以流级声明为准；分段播放列表中途换了编码格式时，画面可能跟随新段的声明，轨道信息不随之更新。`displayWidth` / `displayHeight` 是转正后的尺寸。DV P5 系统显示路径不应用旋转，仍按存储方向显示，轨道的 `rotation` 照实报告 |
| 画面颜色 | 像素路径支持亮度、对比度与饱和度；暂停时重绘，截图使用相同设置，字幕颜色不随画面调节；P5 系统路径不支持 |
| 音频输出 | `SampleBufferAudioOutput` 与 `EngineAudioOutput`；多声道实际输出取决于设备、系统路由及宿主配置 |
| 对象音频 | E-AC-3 (JOC) 交系统播放器按设备渲染，画面跟随其时钟；需 `SampleBufferAudioOutput` 与已知片长，可关闭；失败时退回引擎解码多声道基础层；缓冲内的前跳保留缓存，向后、远跳和已被放掉的短距离前跳重读。TrueHD 中的对象信息不支持，AC-4 不能解码 |
| 音频延迟 | 调整不重新定位，保留播放／暂停状态；已准备的音频会先排空，过渡可插入静音或跳过重叠声音 |
| 缓存音频 | 查询已保留压缩包的时间覆盖，并异步、可取消地提取 PCM；不读取缺失来源、不改变播放位置 |
| 画中画 | `UmbelUI` 提供接入封装；是否可启动需结合系统、显示层和当前内容判断。iOS 上 App 在后台时从小窗还原，还原动画可能短暂（约 0.7 s）显示较早的一帧：后台 App 的界面不更新，系统用它做还原动画；从前台关闭画中画不受影响 |
| 默认播放器 UI | 尚未提供完整控制栏、手势、设置与无障碍交互；宿主负责界面 |

缓存音频接口当前返回分平面的 Float32 PCM 与实际覆盖区间，不提供封装媒体文件的导出接口。
识别、分析与分段算法属于调用方。具体缓存上限、取消和时间戳约定见 [接口说明](playback-controls.md)。

## 系统显示路径

DV P5 播放经系统显示层，需支持该内容的系统与设备，以及 `SampleBufferVideoRenderer` 或包含它的 `SwitchingVideoRenderer`。
此前已在 Mac 和 iPad 完成实际 P5 播放验收；播放通过不等于截图和任意画面变形也已通过。
对已知 10-bit 4:2:0、全范围或未声明范围、无旋转的 P5，优先由系统硬解出全范围原生像素，
保留系统附件并按安全解码时间界限整理显示顺序，再交系统显示层。解码前验证配置，保留的像素表面有数量与字节上限。
此 P5 原生像素路径在 iOS / iPadOS 17 及以上才启用；15 / 16 直接使用现有系统压缩路径。
这是强制硬解选项的系统版本限制，不改变包声明的最低部署版本。
系统拒绝或无法安全排序时，本次会话有界退回系统压缩路径，保留关键帧依赖与已读参数集；不退回普通基础层或启用软件 P5 处理。
本轮 Mac 的 4K / 25 fps 本地 P5 样片验证了此路径的连续播放；同帧两平面的原始像素与系统压缩路径一致。
该新增路径尚未在 iPad 实测，单一样片的验证不代表所有内容、系统版本或显示设备均已验收。
本轮 Mac 追加观察到画面最外沿 1–2 像素闪烁：独立 `AVSampleBufferDisplayLayer` 压缩输入、原生像素输入及固定同帧持续提交均可复现，
同位置、同片段的系统播放器显示层对照正常。丢帧为零不代表这个边缘显示问题已解决；其内部原因与可靠修复尚未确定。

| 输出路径 | 比例覆盖 | fit / fill | 截图 | 颜色调节 | 字幕 |
|---|---|---|---|---|---|
| Metal / 离屏像素路径 | 支持 | 支持 | 首帧呈现后支持 | 支持 | 可合成 |
| 系统显示层的合成像素路径 | 支持 | 当前报告不支持 | 首帧呈现后支持 | 支持 | 可合成；SDR 与目标精度分别选择 |
| DV P8.4 原始系统像素路径 | 当前不支持 | 支持 | `.unsupported(.systemDisplay)` | 当前不支持 | 主窗口独立叠层；画中画不合成自绘字幕 |
| DV P5 原始系统像素／压缩码流路径 | 当前不支持 | 支持 | 当前报告 `.unsupported(.systemDisplay)` | 当前不支持 | 主画面可经 Metal 叠加；P5 画中画不含合成字幕 |

P5 比例覆盖尚需协调显示层尺寸、字幕布局与画中画，并非已证明系统永远禁止。
系统像素回读有系统版本、暂停状态和内容限制；P5 回读格式与颜色正确性仍需专门真机验证，当前接口不开放此能力。
DV P8.4 在具备系统解码/显示能力、无旋转且采用自动策略时，保留原始高位深缓冲和附件交系统显示。
系统拒绝时有界回退 HLG 基础层；明确要求 SDR 或兼容基础层时直接采用像素路径。
系统像素通路按解码时间的安全界限整理 B 帧呈现顺序，并限制保留的原生表面；无法安全排序或恢复时明确回退或报错。
发生系统路径故障后，本次播放保持兼容路径，不在每帧或 seek 时反复尝试同一候选。
DV P8.1 与 P8.4 采用同一条规则：系统硬解 DV、画面不旋转、像素格式受支持且采用自动策略时，默认保留原始系统像素交系统显示（动态元数据由系统映射），
接入方用 `compatibleBaseLayer` 可改回 HDR10 基础层，候选创建失败或系统拒绝时有界回退；
P8.2 采用 SDR 基础层；P8.4 的支持不代表其他 P8 类型已经完成动态效果验收。
本 Mac 与 iPad Pro 11 英寸（M4）/ iPadOS 26.3.1 已用真实 RPU 样片验证 P8.4 的 10-bit 系统交付。

## 视频异步解码范围

创建 `PlaybackSession` 时通过 `videoDecodingMode` 明确选择 `.synchronous`（默认）或 `.asynchronous`。
异步模式以私有串行队列进行单包前瞻，在上一包的帧等待渲染容量时可解码下一包，最多两个在途包任务；
这是引擎级提交与结果消费分离，不是原生 VideoToolbox 提交／完成回调模式。两种模式都在界面线程外解码，
硬件优先、软件回退和软件解码器内部线程行为不变，音频与缩略图解码不变。
下一包未到达时可能增加一个包间隔的启动延迟；不承诺性能提升。

模式在 session 生命周期内不可变，更换需停止旧实例并建立新来源和 session。
`videoDecodingStatus` 区分未启用视频的 `.inactive`、两种引擎模式与 `.systemManaged`；临时挂起时仍表示选中的路径。
DV P5 始终由系统路径管理，不受请求模式影响，也不启用软件处理。
接口示例、在途任务与状态语义见 [播放控制说明](playback-controls.md#video-decoding-mode)。

## 视频解码器偏好与软解线程数

创建 `PlaybackSession` 时通过 `videoDecoder: UmbelVideoDecoderConfiguration` 指定（默认与以前完全一样）：

- `preference`：`.hardware`（默认）能硬解就硬解、硬解不了回退软解；`.software` 一律软解，即使硬件本来可以解。偏好而非强制：系统解码的画面（DV P5、
  由系统解码的 P8.1／P8.4 像素）不经过这条路径，不受影响，音频与缩略图解码也不变。
- `softwareThreadCount`：软解的线程数，只在软解时有效（偏好软解，或硬解不了而回退）。`nil` 由解码器自己定（核数加一，最多 16）。
  取值为 `softwareThreadCounts` 里的 1、2、4、6、8、10、12、14、16；其它值向下取档（7 → 6），小于 1 取 1，大于 16 取 16。
- 帧线程的代价：H.264、HEVC、VP9 等多数编码在线程数为 *n* 时，首幅画面与每次跳转后的首幅画面晚 *n* − 1 帧，并多占 *n* 帧在途画面的内存
  （4K 10 位每帧约 25 MB）。线程少响应快、占用小，多的是给少线程跟不上的高分辨率片源。AV1 由单独的解码库按自己的方式分工，
  延迟为线程数的平方根（向上取整，16 线程时 4 帧）。

两项在会话生命周期内不变：后台回来、跳转后重建、播放列表换了编码、DV 被系统拒绝后改解基础层，重建的解码器都沿用。更换需停止旧实例并新建 session。

`videoDecoderStatus` 报告实际情况：`.hardware`、`.software(threads:)`、`.systemManaged`，未启用视频时为 `.inactive`。
VideoToolbox 在读到码流头之后才可能拒绝一个码流（例如过小的画面）；这时 FFmpeg 会悄悄改用软解，且只带着为硬件打开时的一条线程。
引擎在读到码流头的那个包上发现这种情况，就按软解的设置重新打开解码器并把该包再送一次，不丢帧、不重复，状态也如实显示为软解。
